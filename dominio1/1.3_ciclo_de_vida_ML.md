# AWS Certified AI Practitioner --- Tarefa 1.3 Descrever o ciclo de vida do desenvolvimento de ML

A ideia central desta tarefa é entender como um modelo de ML sai dos
dados e chega à produção, como pode ser obtido, como é disponibilizado
aos usuários, como é operado continuamente e como medimos se ele
realmente funciona.

## 🧩 1. Componentes de um pipeline de IA/ML

``` text
DADOS
  ↓
EXPLORAÇÃO / EDA
  ↓
PRÉ-PROCESSAMENTO
  ↓
ENGENHARIA DE ATRIBUTOS
  ↓
TREINAMENTO
  ↓
AJUSTE DE HIPERPARÂMETROS
  ↓
AVALIAÇÃO
  ↓
IMPLANTAÇÃO / DEPLOYMENT
  ↓
MONITORAMENTO
  ↓
RETREINAMENTO
  ↺
```

> **🔥 DECORA:** ML não termina quando o modelo é treinado. Em produção,
> ele precisa ser implantado, monitorado e, quando necessário,
> retreinado.

### 📥 1. Coleta de dados

Obtenção dos dados que serão usados para desenvolver e avaliar o modelo.

Exemplos: - dados de clientes; - transações; - imagens; - textos; -
sensores; - históricos de vendas.

> **DECORA:** sem dados adequados, não existe modelo confiável.

### 🔎 2. Análise exploratória de dados --- EDA

Exploração dos dados para entender sua estrutura, qualidade,
distribuição e possíveis problemas.

Pode envolver: - identificar valores ausentes; - detectar outliers; -
observar distribuições; - identificar correlações; - verificar
desequilíbrio entre classes; - entender características dos dados.

> **PEGADINHA:** EDA não é treinamento do modelo. É entender os dados
> **antes** de treinar.

### 🧹 3. Pré-processamento

Preparação dos dados para que possam ser utilizados adequadamente pelo
algoritmo.

Exemplos: - tratar valores ausentes; - remover ou tratar dados
inválidos; - normalizar valores; - codificar categorias; - limpar
textos; - transformar formatos.

> **DECORA:** pré-processamento = **preparar os dados**.

### 🧬 4. Engenharia de atributos --- Feature Engineering

Criação, transformação ou seleção de atributos (features) relevantes
para melhorar o aprendizado do modelo.

Exemplo:

``` text
Data da compra
      ↓
Dia da semana
      ↓
Final de semana? = SIM/NÃO
```

> **DECORA:** Feature Engineering = transformar dados em atributos úteis
> para o modelo.

### 🧠 5. Treinamento do modelo

O algoritmo aprende padrões a partir dos dados de treinamento.

``` text
Dados de treinamento
        ↓
    Algoritmo
        ↓
      Modelo
```

> **DECORA:** treinamento = **aprender**.

### ⚙️ 6. Ajuste de hiperparâmetros

Hiperparâmetros são configurações definidas para controlar o processo de
treinamento. O ajuste busca encontrar configurações que produzam melhor
desempenho.

Exemplos conceituais: - taxa de aprendizado; - número de árvores; -
profundidade de árvore; - tamanho de lote.

> **PEGADINHA:** hiperparâmetro ≠ parâmetro aprendido pelo modelo
> durante o treinamento.

### 📊 7. Avaliação

O modelo é testado para determinar se consegue produzir boas previsões
em dados apropriados, normalmente separados dos dados usados para
treinamento.

Pode utilizar: - Accuracy; - Precision; - Recall; - F1; - AUC; - outras
métricas adequadas ao problema.

> **DECORA:** treinamento = aprender; avaliação = verificar se aprendeu
> bem.

### 🚀 8. Implantação --- Deployment

Disponibilização do modelo para ser utilizado por uma aplicação, usuário
ou sistema.

``` text
Aplicação
   ↓
API
   ↓
Modelo
   ↓
Predição
```

O modelo pode ser disponibilizado por: - API gerenciada; - API
auto-hospedada.

### 👀 9. Monitoramento

Depois de entrar em produção, o modelo precisa ser acompanhado
continuamente.

Pode-se observar: - desempenho; - latência; - erros; - qualidade das
previsões; - comportamento dos dados; - custos; - indicadores do
negócio.

> **🔥 DECORA:** modelo em produção ≠ modelo esquecido.

## 📋 O pipeline completo

  Etapa                   Pergunta principal
  ----------------------- -----------------------------------------
  Coleta                  De onde vêm os dados?
  EDA                     O que existe nesses dados?
  Pré-processamento       Como preparar os dados?
  Feature Engineering     Quais atributos serão utilizados?
  Treinamento             Como o modelo aprende?
  Hyperparameter Tuning   Quais configurações funcionam melhor?
  Avaliação               O modelo funciona adequadamente?
  Deployment              Como colocá-lo em produção?
  Monitoramento           Ele continua funcionando adequadamente?
  Retreinamento           É necessário atualizar o modelo?

## 🧩 2. Origens dos modelos de ML

Um modelo pode ser utilizado de diferentes maneiras. O exame destaca
principalmente modelos pré-treinados de código aberto e modelos
personalizados treinados.

### 🟢 Modelo pré-treinado

Modelo que já foi treinado anteriormente e pode ser utilizado ou
adaptado para uma tarefa.

``` text
Modelo já treinado
       ↓
   adaptar / usar
       ↓
   aplicação
```

Vantagens: - desenvolvimento mais rápido; - menor necessidade de
treinamento do zero; - pode reduzir custo e tempo.

> **DECORA:** pré-treinado = modelo que já passou por treinamento.

### 🟡 Modelo de código aberto

Modelos disponibilizados publicamente sob determinadas licenças,
permitindo uso, adaptação ou execução conforme os termos da licença.

É necessário considerar: - licença; - infraestrutura; - custo; -
segurança; - capacidade de customização; - requisitos operacionais.

> **PEGADINHA:** código aberto não significa automaticamente "sem
> custo", "sem restrições" ou "sem necessidade de infraestrutura".

### 🔴 Modelo personalizado

Modelo treinado ou adaptado especificamente para uma necessidade
determinada.

``` text
Dados específicos
       ↓
Treinamento / adaptação
       ↓
Modelo personalizado
       ↓
Caso de uso específico
```

Pode fazer sentido quando: - o problema é muito específico; - dados
próprios são importantes; - é necessário maior controle; - um modelo
existente não atende suficientemente ao caso de uso.

> **🔥 DECORA:**\
> Pré-treinado → mais rápido para começar.\
> Personalizado → maior adaptação ao caso específico.

## 🚀 3. Como colocar um modelo em produção?

### ☁️ API gerenciada

Um provedor de serviço gerencia grande parte da infraestrutura
necessária para disponibilizar o modelo.

``` text
Aplicação
   ↓
API gerenciada
   ↓
Modelo
```

Vantagens: - menor carga operacional; - infraestrutura gerenciada; -
escalabilidade mais simples; - desenvolvimento mais rápido.

> **DECORA:** API gerenciada = **menos infraestrutura para
> administrar**.

### 🖥️ API auto-hospedada

A organização executa e gerencia a infraestrutura necessária para
hospedar o modelo e disponibilizá-lo por uma API.

``` text
Aplicação
   ↓
API da organização
   ↓
Infraestrutura própria
   ↓
Modelo
```

A organização pode precisar administrar: - servidores; - containers; -
escalabilidade; - atualizações; - disponibilidade; - segurança; -
modelo; - custos de infraestrutura.

> **DECORA:** self-hosted = **mais controle + mais responsabilidade
> operacional**.

### ⚖️ Managed API × Self-hosted

  -----------------------------------------------------------------------
  Característica          API gerenciada          API auto-hospedada
  ----------------------- ----------------------- -----------------------
  Infraestrutura          Provedor gerencia       Organização gerencia
                          grande parte            

  Controle                Menor                   Maior

  Operação                Mais simples            Mais complexa

  Escalabilidade          Geralmente mais simples Responsabilidade da
                                                  organização

  Infraestrutura própria  Menos necessária        Necessária

  Carga operacional       Menor                   Maior
  -----------------------------------------------------------------------

> **PEGADINHA:** auto-hospedada não significa necessariamente servidor
> físico próprio. Pode utilizar infraestrutura de nuvem que a própria
> organização administra.

## ☁️ 4. AWS no pipeline de IA/ML

### 🧠 Amazon SageMaker AI

Serviço da AWS voltado ao desenvolvimento e operação de soluções de ML,
incluindo atividades relacionadas a construção, treinamento,
customização e implantação de modelos.

``` text
Dados
 ↓
Preparação
 ↓
Treinamento
 ↓
Avaliação
 ↓
Deployment
 ↓
Monitoramento
```

> **DECORA:** **SageMaker AI = ML / ciclo de vida de modelos.**

### 🤖 Amazon Bedrock

Serviço gerenciado para trabalhar com modelos de base (Foundation
Models) e construir aplicações de IA generativa.

``` text
Aplicação
    ↓
Amazon Bedrock
    ↓
Foundation Model
    ↓
Resposta
```

> **DECORA:** **Bedrock = acesso a Foundation Models / GenAI.**

### 💬 Amazon Q

Família de assistentes de IA generativa da AWS voltados a diferentes
necessidades, incluindo produtividade e desenvolvimento.

> **DECORA:** Amazon Q = **assistente de IA**.

### ⚡ Amazon Quick

Serviço da AWS incluído no escopo atual do exame para aplicações de IA
generativa e produtividade/insights.

> **ATENÇÃO:** não confunda **Amazon Quick** com **Amazon QuickSight**.
> O guia atual do AIF-C01 lista Amazon Quick separadamente.

### 👨‍💻 Kiro

Ferramenta de desenvolvimento da AWS com recursos orientados por IA.

> **DECORA:** Kiro = **desenvolvimento assistido por IA**.

### 🧩 Mapa AWS

``` text
                  IA / ML
                     │
        ┌────────────┴────────────┐
        │                         │
   ML tradicional             GenAI / FM
        │                         │
        ▼                         ▼
SageMaker AI                 Bedrock
        │                         │
        │                    Modelos de base
        │                         │
        └────────────┬────────────┘
                     │
              Aplicações IA
                     │
             ┌───────┴───────┐
             ▼               ▼
        Amazon Q           Amazon Quick
             │

```

> **🔥 PROVA:** se a questão falar em **construir/treinar/deploy de
> modelos ML**, pense primeiro em **SageMaker AI**. Se falar em **acesso
> a Foundation Models e GenAI**, pense em **Amazon Bedrock**.

## ⚙️ 5. MLOps

**MLOps (Machine Learning Operations)** é o conjunto de práticas para
colocar modelos de ML em produção de maneira confiável, repetível,
escalável e sustentável.

``` text
Desenvolver
    ↓
Experimentar
    ↓
Validar
    ↓
Produzir
    ↓
Monitorar
    ↓
Atualizar
    ↺
```

O guia destaca: - experimentação; - processos repetíveis; - sistemas
escaláveis; - gerenciamento de dívida técnica; - prontidão para
produção; - monitoramento; - retreinamento.

### 🧪 Experimentação

Testar diferentes dados, modelos, algoritmos e configurações para
descobrir uma solução adequada.

> **DECORA:** MLOps precisa tornar experimentos rastreáveis e
> reproduzíveis.

### 🔁 Processos repetíveis

O processo de treinamento, avaliação e deployment deve poder ser
repetido de forma consistente.

``` text
Código + Dados + Configuração
             ↓
       Mesmo processo
             ↓
       Resultado reproduzível
```

Automação ajuda a evitar processos manuais inconsistentes.

### 📈 Sistemas escaláveis

A solução deve conseguir lidar com o aumento de dados, usuários e
requisições sem exigir uma reconstrução completa da arquitetura.

``` text
100 usuários
     ↓
1.000 usuários
     ↓
100.000 usuários
```

### 🧾 Dívida técnica

Dívida técnica ocorre quando decisões ou atalhos feitos durante o
desenvolvimento geram trabalho adicional ou problemas no futuro.

Exemplos: - código difícil de manter; - processos manuais; - falta de
testes; - pipelines não automatizados; - documentação insuficiente; -
modelos sem rastreabilidade.

> **DECORA:** dívida técnica = **problema futuro criado por soluções ou
> atalhos de hoje**.

### 🚀 Prontidão para produção

Antes de colocar o modelo em produção, é necessário considerar: -
desempenho; - segurança; - confiabilidade; - escalabilidade; - custo; -
monitoramento; - integração; - operação; - requisitos do negócio.

> **PEGADINHA:** modelo com boa métrica de teste ≠ automaticamente
> pronto para produção.

### 👀 Monitoramento de modelos

Depois do deployment, o modelo precisa ser acompanhado para identificar
degradação de desempenho, mudanças nos dados ou problemas operacionais.

``` text
Modelo em produção
       ↓
   Monitoramento
       ↓
Problema detectado?
    ↙         ↘
  NÃO         SIM
   ↓           ↓
Continuar   Investigar
               ↓
          Retreinar?
```

### 🔄 Retreinamento

Quando os dados ou o comportamento do problema mudam, o modelo pode
precisar ser atualizado ou treinado novamente.

``` text
Dados antigos
     ↓
Modelo
     ↓
Produção
     ↓
Dados mudam
     ↓
Desempenho cai
     ↓
Retreinamento
     ↓
Novo modelo
```

> **DECORA:** modelo de ML pode **degradar com o tempo** porque o mundo
> e os dados mudam.

## 📊 6. Métricas de desempenho do modelo

As métricas de modelo avaliam **quão bem o modelo está fazendo sua
tarefa**.

### 🎯 Accuracy --- Acurácia

Percentual de previsões corretas em relação ao total de previsões.

``` text
Accuracy =
previsões corretas
──────────────────
total de previsões
```

Exemplo:

``` text
100 previsões
90 corretas

Accuracy = 90%
```

> **DECORA:** Accuracy = **"quantas previsões no total eu acertei?"**

### ⚠️ Pegadinha da Accuracy

Accuracy pode ser enganosa quando as classes estão muito
desequilibradas.

Exemplo:

``` text
1000 transações
990 normais
10 fraudulentas
```

Um modelo que classifique tudo como "normal":

``` text
990 acertos / 1000 = 99% Accuracy
```

Mas ele não detectou nenhuma fraude.

### 🎯 Precision --- Precisão

Entre todas as previsões positivas feitas pelo modelo, quantas realmente
eram positivas.

``` text
Precision =
TP
──────────
TP + FP
```

Pergunta mental:

> **"Quando o modelo disse POSITIVO, quantas vezes ele estava certo?"**

Exemplo:

``` text
Modelo marcou 100 transações como fraude
80 eram realmente fraude

Precision = 80%
```

> **DECORA:** Precision olha para os **positivos previstos**.

### 🔎 Recall --- Revocação / Sensibilidade

Entre todos os positivos que realmente existem, quantos o modelo
conseguiu identificar.

``` text
Recall =
TP
──────────
TP + FN
```

Pergunta mental:

> **"De todas as fraudes que realmente existiam, quantas eu
> encontrei?"**

Exemplo:

``` text
Existiam 100 fraudes
modelo encontrou 90

Recall = 90%
```

> **DECORA:** Recall olha para os **positivos reais**.

### ⚖️ F1 Score

É a média harmônica entre Precision e Recall.

``` text
F1 =
2 × Precision × Recall
──────────────────────
Precision + Recall
```

> **DECORA:** F1 = **equilíbrio entre Precision e Recall**.

### 🧠 Tabela definitiva

  Métrica     Pergunta mental
  ----------- ----------------------------------------------------------
  Accuracy    Quantos acertos tive no total?
  Precision   Dos positivos que previ, quantos estavam certos?
  Recall      Dos positivos que realmente existiam, quantos encontrei?
  F1          Como equilibrar Precision e Recall?

``` text
                 CLASSIFICAÇÃO

Accuracy  → acertos / total

Precision → positivos previstos
            "Quando digo POSITIVO, estou certo?"

Recall    → positivos reais
            "Encontrei os POSITIVOS que existiam?"

F1        → equilíbrio
            "Como combinar Precision + Recall?"
```

## 💰 7. Métricas de negócio

Um modelo pode apresentar excelentes métricas técnicas e ainda assim não
gerar valor para a empresa.

### 💰 Custo por usuário

Quanto custa atender cada usuário utilizando a solução.

``` text
Custo total
───────────
nº usuários
```

### 💵 Custos de desenvolvimento

Quanto foi gasto para construir e colocar a solução em funcionamento.

Pode envolver: - desenvolvimento; - infraestrutura; - dados; -
treinamento; - integração; - operação.

### 💬 Feedback dos clientes

Avalia a percepção dos usuários sobre a solução.

Exemplos: - satisfação; - reclamações; - avaliações; - aceitação; - taxa
de uso.

### 📈 ROI --- Return on Investment

Avalia o retorno obtido em relação ao investimento realizado.

Conceitualmente:

``` text
ROI =
retorno obtido
──────────────
investimento
```

> **DECORA:** métrica técnica responde **"o modelo funciona?"**; métrica
> empresarial responde **"isso gera valor?"**.

## ⚖️ 8. Modelo bom ≠ negócio bom

Imagine:

``` text
Modelo A
Accuracy = 95%
```

Parece excelente.

Mas:

``` text
Custo por usuário = muito alto
Infraestrutura = cara
Latência = alta
Clientes = insatisfeitos
ROI = negativo
```

Então o modelo pode ter boa performance técnica e, mesmo assim, não ser
uma boa solução empresarial.

> **🔥 PROVA:** não confunda **performance do modelo** com **sucesso do
> negócio**.

## 🔥 10. DECORAÇÃO FINAL --- O que realmente memorizar

> **1. Pipeline:** Dados → EDA → Pré-processamento → Features →
> Treinamento → Tuning → Avaliação → Deployment → Monitoramento.

> **2. Treinamento:** modelo aprende.

> **3. Avaliação:** verifica desempenho.

> **4. Deployment:** coloca o modelo em produção.

> **5. Monitoramento:** acompanha o modelo em produção.

> **6. Retreinamento:** atualiza o modelo quando necessário.

> **7. SageMaker AI:** pense em ciclo de vida de ML.

> **8. Bedrock:** pense em Foundation Models e GenAI.

> **9. Managed API:** menos infraestrutura para administrar.

> **10. Self-hosted:** mais controle, mais responsabilidade operacional.

> **11. Accuracy:** acertos totais.

> **12. Precision:** "dos positivos que previ, quantos estavam certos?"

> **13. Recall:** "dos positivos reais, quantos encontrei?"

> **14. F1:** equilíbrio entre Precision e Recall.

> **15. Métrica técnica:** "o modelo funciona?"

> **16. Métrica de negócio:** "o modelo gera valor?"

## ⚠️ PEGADINHAS DE PROVA

-   **EDA ≠ treinamento.**
-   **Pré-processamento ≠ Feature Engineering.**
-   **Treinamento ≠ avaliação.**
-   **Modelo treinado ≠ modelo pronto para produção.**
-   **Deployment ≠ monitoramento.**
-   **API gerenciada ≠ API auto-hospedada.**
-   **Código aberto ≠ necessariamente gratuito.**
-   **Accuracy alta ≠ necessariamente bom modelo**, principalmente com
    classes desbalanceadas.
-   **Precision ≠ Recall.**
-   **Boa métrica de ML ≠ necessariamente bom resultado empresarial.**
-   **MLOps não é apenas deployment:** envolve experimentação,
    repetibilidade, escalabilidade, operação, monitoramento e
    retreinamento.
